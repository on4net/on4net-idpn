# on4net IDPN — سامانه هویت و دسترسی یکپارچه

> **نسخه:** 0.4 (چندزبانه per-app و Login Contexts اضافه شد)
> **تاریخ:** 2026-10-18
> **وضعیت:** استک، میکرو-فرانت‌اند، shadcn/ui، سوشال لاگین، چندزبانه per-app، چند مدل ورود per-app و الزام تست تأیید شد؛ جزئیات باز در بخش ۷.

## 1. خلاصه اجرایی

هدف این پروژه ساخت یک **Identity Provider مرکزی** (سامانه هویت) برای مجموعه‌ای از پلتفرم‌های موجود است. همه پلتفرم‌ها به‌جای داشتن نام کاربری و رمز عبور مستقل، احراز هویت را به این سامانه می‌سپارند. نتیجه:

- کاربر با یک بار ورود در هر پلتفرم، در بقیه پلتفرم‌ها هم وارد می‌شود (**SSO**).
- کاربران، نقش‌ها و مجوزها به‌صورت مرکزی مدیریت می‌شوند.
- هر پلتفرم فقط نقش‌ها و مجوزهای مرتبط با خودش را می‌بیند.
- رابط ورود مشترک روی دامنه IdP و ماژول‌های پروفایل/مدیریت کاربری به‌صورت **میکرو-فرانت‌اند** در اپ‌ها استفاده می‌شوند؛ هر اپ فقط کاربران و نقش‌های خودش را می‌بیند.
- ورود با Google/Facebook با **Credential اختصاصی هر اپلیکیشن** پشتیبانی می‌شود.
- هر اپ می‌تواند **چند مدل ورود** داشته باشد (مدیر مشتری، تیم مشتری، تیم ادمین و…) با نقش‌ها، روش‌های ورود، MFA و ظاهر مستقل.
- هر اپ می‌تواند **زبان، جهت متن و متن‌های خودش** را داشته باشد (فارسی/انگلیسی و افزودنی) بدون Fork کردن UI.
- خروج، مدیریت نشست‌ها، بازیابی رمز عبور، ورود دومرحله‌ای و گزارش‌های حسابرسی یک‌جا انجام می‌شود.
- تست‌های Unit، Integration و E2E بخشی از تحویل هر قابلیت هستند.

سامانه روی پروتکل‌های استاندارد **OpenID Connect 1.0** و **OAuth 2.1** بنا می‌شود تا هر پلتفرم با کتابخانه‌های معتبر موجود به آن متصل شود و وابستگی به فناوری خاصی نداشته باشد. بک‌اند **Node.js** و دیتابیس **PostgreSQL** است؛ فرانت‌اند با **React + Vite** و خروجی میکرو-فرانت‌اند سازگار با میزبان‌های مختلف ارائه می‌شود.

## 3. دامنه

### داخل دامنه (فاز اول)

- سرور احراز هویت (Authorization Server) سازگار با OIDC/OAuth 2.1
- مدیریت کاربران، پروفایل، رمز عبور و نشست‌ها
- رجیستری کلاینت‌ها (پلتفرم‌ها) و کلیدهای آن‌ها
- میکرو-فرانت‌اند مشترک: صفحه ورود Hosted + ماژول‌های `account` و `user-management` با نسخه‌بندی مستقل
- مدیریت کاربری scoped برای هر اپلیکیشن (`ClientMembership`) و ادمین واگذارشده (Delegated Admin)
- سوشال لاگین Google/Facebook با Credential اختصاصی هر اپ
- چندزبانه بودن per-app: بسته پایه `fa`/`en`، Override متن هر اپ، RTL/LTR، تاریخ و اعداد با Locale
- مدل‌های ورود per-app (Login Contexts): چند درگاه ورود در یک اپ با نقش‌ها و سیاست‌های مستقل
- Design System مشترک با shadcn/ui، Tailwind v4 و توکن‌های OKLCH
- نقش‌ها، مجوزهای قابل تعریف توسط هر اپ و تخصیص آن‌ها در سطح سراسری/سازمان
- انتشار نقش/مجوز و ویژگی‌های اختصاصی اپ در توکن دسترسی همان پلتفرم
- پنل مدیریت (Admin Panel) روی دامنه مستقل
- خروج محلی و سراسری + Back-channel Logout
- ورود دومرحله‌ای (TOTP/WebAuthn) در فاز تکمیلی
- Audit Log و مدیریت کلیدهای امضا
- تست Unit، Integration، Contract و E2E با پوشش جریان‌های چنداپلیکیشنی

### خارج از دامنه (فاز اول)

- صورت‌حساب و اشتراک
- API Gateway و مدیریت ترافیک
- ذخیره‌سازی داده‌های کسب‌وکار پلتفرم‌ها
- بازنویسی مستقل UI ورود/مدیریت کاربری در هر اپ (همه باید از MFE مشترک استفاده کنند)
- تصمیم‌های سطح ردیف داده (Row-level) داخل اپ‌ها؛ IdP فقط هویت، نقش و مجوز صادر می‌کند
- Passwordless کامل (فقط به‌عنوان مسیر آینده)
- حکمرانی داده و انطباق حقوقی فراتر از حداقل‌های امنیتی

## 4. اصول طراحی

1. **استاندارد قبل از اختراع:** پیاده‌سازی روی OIDC/OAuth 2.1 و کتابخانه‌های شناخته‌شده؛ هیچ مکانیزم اختصاصی برای ورود پلتفرم‌ها ساخته نمی‌شود.
2. **توکن کوتاه‌عمر:** Access Token کوتاه (پیش‌فرض 10 دقیقه) و Refresh Token چرخشی با تشخیص استفاده مجدد.
3. **حداقل دسترسی:** پیش‌فرض «رد» است؛ هر پلتفرم فقط مجوزهای همان پلتفرم را دریافت می‌کند.
4. **جداسازی نقش‌ها:** نقش‌های مدیریت IdP کاملاً از نقش‌های اپلیکیشن‌ها جدا هستند.
5. **بی‌اعتمادی به کلاینت:** تصمیم‌های دسترسی در سرور گرفته می‌شود؛ پنهان‌کردن دکمه در UI جایگزین بررسی سروری نیست.
6. **قابلیت حسابرسی:** هر رویداد حساس (ورود، تغییر نقش، ابطال نشست، تغییر کلاینت) ثبت می‌شود.
7. **آمادگی چندسازمانی:** `tenant_id` از ابتدا در مدل داده وجود دارد، حتی اگر فاز اول تک‌سازمانی باشد.
8. **بی‌طرفی فناوری در سمت کلاینت:** پلتفرم‌ها با هر استکی فقط باید OIDC را پیاده کنند.
9. **یک UI، چند اپلیکیشن:** ورود روی دامنه IdP میزبانی می‌شود و مدیریت حساب/کاربری به‌صورت میکرو-فرانت‌اند با `clientId` و تنظیمات هر اپ رندر می‌شود؛ Fork کردن UI ممنوع است.
10. **مرز داده‌ای هر اپ:** ادمین هر اپ فقط اعضای همان اپ را می‌بیند؛ محدودیت در سرور اعمال می‌شود، نه فقط در UI.
11. **آزمون‌پذیری:** هر قابلیت با تست Unit/Integration/E2E و قرارداد نسخه‌دار تحویل می‌شود.
12. **زبان بخشی از هویت اپ است:** زبان و متن هر اپ از تنظیمات همان کلاینت می‌آید، نه از کد مشترک؛ Override مجاز، Fork ممنوع.
13. **هر درگاه ورود یک مرز دسترسی است:** هر Login Context فقط نقش‌های مجاز خودش را می‌دهد و Claim `login_context` مرز را در توکن ثابت می‌کند.

## 7. پرسش‌های باز (برای تأیید پیش از ثبت تسک)

> **نکته تصمیم:** فرم ورود (رمز/سوشال) به‌صورت Embedded داخل دامنه اپ‌ها پشتیبانی نمی‌شود؛ چون کوکی نشست IdP در Context سایت دیگر محدود می‌شود و SSO ناپایدار/ناامن می‌گردد. ورود با Redirect سطح‌بالا به Hosted Auth UI انجام می‌شود، اما ماژول‌های `account` و `user-management` به‌صورت میکرو-فرانت‌اند داخل اپ Mount می‌شوند. اگر نیاز قطعی به Embedded Login دارید، بفرمایید تا گزینه‌های پرریسک و پیامدهای آن بررسی شود.

1. **میزبان‌ها:** اپلیکیشن‌های میزبان با چه فریمورک‌هایی نوشته شده‌اند (React، Vue، Angular، legacy)؟ آیا همه React هستند یا Web Component هم لازم است؟
2. **سوشال:** به‌جز Google و Facebook، Provider دیگری (GitHub، LinkedIn، Apple، Microsoft) لازم است؟
3. **داده اختصاصی هر اپ:** هر اپ چه فیلدهای پروفایل یا ویژگی‌های اختصاصی کاربر را نیاز دارد که باید در `ClientMembership.attributes` ذخیره شود؟
4. **پلتفرم‌ها و دامنه‌ها:** چند اپلیکیشن وصل می‌شوند و دامنه‌هایشان چیست؟ زیردامنه یک دامنه والد هستند یا متفاوت؟
5. **کاربران فعلی:** آیا هر اپ الان کاربر دارد؟ مهاجرت چگونه باشد؟ (رمز عبور قابل انتقال نیست و باید بازنشانی شود.)
6. **ساختار سازمانی:** چند سازمان/شرکت مستقل وجود دارد یا یک سازمان واحد؟
7. **روش ورود:** ایمیل، نام کاربری، موبایل + OTP، یا ترکیبی؟
8. **MFA:** اجباری برای همه، اختیاری، یا فقط ادمین‌ها و نقش‌های حساس؟
9. **ثبت‌نام:** فقط دعوت ادمین یا ثبت‌نام آزاد هم داشته باشیم؟ آیا سیاست هر اپ متفاوت است؟
10. **استقرار:** سرور اختصاصی، Docker، Kubernetes یا ابر؟ الزام on-premise وجود دارد؟
11. **حجم و SLA:** تعداد کاربران، ورود روزانه و SLA مورد انتظار؟
12. **انطباق:** الزام نگهداشت لاگ، حذف داده کاربر یا ممیزی خاصی وجود دارد؟
13. **APIهای ثالث:** سرویس‌های بیرونی هم باید توکن بگیرند یا فقط اپ‌های داخلی؟
14. **برندینگ:** هر اپ تم/لوگو/دامنه ورود اختصاصی می‌خواهد یا ظاهر یکسان کافی است؟
15. **زبان‌ها:** هر اپ کدام زبان‌ها را لازم دارد (fa، en، ar، …) و آیا اپ می‌خواهد متن‌های خودش را Override کند؟
16. **تصمیم زبان:** زبان پیش‌فرض کل سامانه فارسی باشد یا هر اپ زبان خودش را داشته باشد؟
17. **مدل‌های ورود:** برای هر اپ کدام Contextها لازم است (مثلاً مدیر مشتری، تیم مشتری، تیم ادمین، پشتیبانی)؟
18. **مالکیت Context:** تعریف Contextها فقط با ادمین سراسری انجام شود یا ادمین هر اپ هم بتواند Context بسازد؟
19. **تقویم:** نمایش تاریخ شمسی برای همه اپ‌ها الزامی است یا به‌ازای هر کلاینت قابل تنظیم باشد؟

## 8. واژه‌نامه

| اصطلاح | معنا |
|---|---|
| IdP | Identity Provider؛ سامانه مرکزی هویت |
| OP / AS | OpenID Provider / Authorization Server؛ همان سرور IdP |
| RP / Client | پلتفرمی که از IdP برای ورود استفاده می‌کند |
| SSO | Single Sign-On؛ ورود یک‌بار و استفاده در چند پلتفرم |
| OIDC | لایه هویت روی OAuth 2.0 برای دریافت ID Token |
| PKCE | Proof Key for Code Exchange؛ محافظت از جریان Code در کلاینت‌های عمومی |
| BFF | Backend-for-Frontend؛ لایه سروری هر پلتفرم برای نگهداری توکن |
| Access Token | توکن دسترسی به API با عمر کوتاه |
| ID Token | توکن هویت کاربر با عمر کوتاه |
| Refresh Token | توکن بلندعمر برای دریافت توکن جدید، چرخشی و یک‌بارمصرف |
| JWKS | مجموعه کلیدهای عمومی برای اعتبارسنجی امضای JWT |
| RBAC | Role-Based Access Control؛ دسترسی بر پایه نقش |
| Claim | فیلد داخل توکن (مثل `sub`، `roles`، `sid`) |
| Tenant | سازمان/مستأجر مستقل در یک نصب مشترک |
| MFE | Micro-Frontend؛ رابط مشترک قابل تزریق در چند اپلیکیشن |
| Host / Remote | اپلیکیشن میزبان / ماژول راه‌دور که در آن بارگذاری می‌شود |
| Module Federation | روش به‌اشتراک‌گذاری ماژول و Dependency بین Buildها |
| Web Component | Custom Element مستقل از فریمورک برای مصرف MFE |
| ClientMembership | عضویت کاربر در یک Context از یک اپلیکیشن با وضعیت و ویژگی‌های اختصاصی |
| Delegated Admin | ادمین محدود به یک اپ یا Context که فقط همان محدوده را مدیریت می‌کند |
| Social Provider Credential | Client ID/Secret اختصاصی هر اپ برای Google/Facebook |
| Login Context | درگاه ورود داخل یک اپ با نقش‌ها، روش‌های ورود و سیاست MFA مستقل |
| Context Admin | ادمین محدود به یک Login Context |
| Locale | زبان و منطقه (مثل `fa-IR`) که جهت متن، فونت و فرمت داده را تعیین می‌کند |
| Translation Override | متن اختصاصی یک اپ که متن پایه را جایگزین می‌کند |
| Dir (RTL/LTR) | جهت چیدمان متن و رابط |
| ICU MessageFormat | قالب پیام برای جمع، انتخاب و Placeholder |
| Test Pyramid | تقسیم تست‌ها به Unit، Integration و E2E |
| Back-channel Logout | اطلاع‌رسانی سروربه‌سرور خروج به همه کلاینت‌ها |
